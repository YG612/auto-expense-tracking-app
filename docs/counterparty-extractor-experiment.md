# 交易对手抽取模型实验

## 定义

交易对手是原文中直接收取用户资金、向用户支付资金，或直接提供商品/服务的一方。模型只能选择原文中的连续跨度，不得补全或生成名称。

以下内容不是交易对手：

- 出发地、目的地及普通地点；
- 购买的商品或服务；
- 支付渠道和账户；
- 受益人、同行人及仅被提及的人；
- 作为商品、证券、礼品卡组成部分出现的品牌；
- 未发生交易时被提及的商户。

## 实验结构

第一阶段通过宽松规则生成候选，允许地点、商品、渠道等误入候选；第二阶段用 fastText 候选判别模型从候选中选择主要交易对手。候选文本以显式边界标记，并带候选来源特征。

数据完全由 Codex 编写的语义模板合成并确定性展开。商户族、人物和城市在训练、验证、冻结测试之间隔离。生成数据位于忽略目录 `data/synthetic/work/counterparty-v1`，训练产物位于忽略目录 `build/model-candidates`。

运行方式：

```powershell
pnpm counterparty-data:generate
pnpm counterparty-model:test
pnpm counterparty-model:train
```

## 重点困难负样本

- “从武汉到上海买动车票”：武汉、上海、动车票都不是交易对手；
- “买某餐厅股票/礼品卡”：品牌不是本次交易对手；
- “支付宝付给某商店”：支付宝是渠道，商店是交易对手；
- “帮张三买药”：张三是受益人，不是交易对手；
- 平台、实际服务商和支付渠道同时出现；
- 否定、未消费、通知缺少商户、泛化地点等文本。

## 训练和验收结果

最终候选模型使用 fastText 字符子词分类器，训练集、验证集和冻结测试分别包含 2250、591 和 1088 条交易。候选行分别为 16260、4086 和 8103 条。选定阈值为 `0.05`。

内部验证结果：

- 候选召回率：99.73%；
- 精确率：99.16%；
- 召回率：95.43%；
- 无交易对手样本误报率：0%。

同生成规范下的冻结测试为 100% 精确率、100% 召回率和 0% 无对象误报。该结果只能说明实现与当前合成规范一致，不能替代真实分布评估。

独立生成的 v8、v9、v10 挑战集依次发现并修复了以下问题：

- “最后没有消费”被“最后”一词错误覆盖；
- “打给/打过来”没有计入真实交易证据；
- 公司名“开元”中的“元”被误当作金额单位；
- “昨晚打款给某人”把“昨晚”当作付款方；
- “商户字段缺失”把占位文本当作商户；
- “公益基金会”中的“基金”被误当作金融产品。

修复后，v9 的 360 条和 v10 的 315 条均全部回归通过；应用内 TypeScript 解析器也直接回放这 675 条样本并全部通过。由于这些集合已参与错误诊断，修复后的结果属于回归证据，不再宣称为未见盲测。

## 端侧集成

模型量化前为 3,233,868 字节，量化后为 343,710 字节。量化模型在 v9 和 v10 回归中未出现指标下降。模型随现有离线分类资产发布，并由 Android 和 iOS 在加载前校验文件大小与 SHA-256。

运行时策略：

1. 规则生成高召回的原文连续跨度候选；
2. 否定交易、行程地点、地点修饰、支付渠道、受益人和金融产品使用硬约束过滤；
3. 明确字段、直接收付款方和明确服务提供方由确定性角色规则解析；
4. 仅在应用仍没有商户/对象时，端侧模型对剩余候选排序；
5. 模型结果标记为“端侧 AI 建议，请确认”，不得自动确认或自动入账；
6. 模型缺失、超时或输出无效时保持原结果，不影响基础记账。

原生 C++ smoke test 已实际加载量化模型并完成候选打分；Android Debug 离线构建已通过。

## 限制

- 所有训练和验收数据均为大模型设计后确定性生成，没有真实账单或人工审计标签；
- 连续跨度之外的别名归一化仍交给已有商户词典处理；
- 未知、无角色线索且没有词典命中的短品牌允许不填，避免把地点或商品强行写入商户；
- 当前结果满足“端侧建议并要求确认”的集成门槛，不足以支持无人确认的自动入账；
- 上线后应只记录匿名化的接受/修改统计，并以用户确认结果建立新的隔离评估集。
