# 轻记 AI 全局产品审计与问题地图（2026-08-22）

> 本文记录提交 `34fb9d0b9947e0eb2c03550ddb1474e34d349e79` 的只读审计结论。审计覆盖记账语义、分类模型、确认交互、分类与账户体系、CSV、预算、周期账、数据库、备份、隐私、通知/OCR、离线语音、性能、无障碍和发布链路。本文不把源码存在、自动测试、APK 可安装、单机观察和生产就绪混为一谈。

## 1. 总体结论

轻记 AI 已经具备值得保留的安全基础：local-first、Android 无网络权限、关键金额由确定性逻辑处理、特殊语义倾向 fail closed、用户确认后写账、语音回调代际隔离、数据库事务幂等、加密备份以及周期账/通知导入只生成待确认记录。

但当前仍是研究与 Internal 验证阶段，不能作为生产主账本发布。最高风险不再只是缺少某个分类词，而是系统还没有独立建模以下金融事件事实：

1. 交易是否已经真实完成；
2. 付款人、收款人和账本所有者分别是谁；
3. 资金是流入、流出还是账户间转移；
4. 文本是事实、计划、提醒、报价、转述、失败还是取消；
5. 押金、预授权、充值、退款、借还款等资金语义是否已经结算。

因此下一阶段应从“继续增加分类词”转为“先建立交易事件门，再做分类”。同时必须修复预算二级分类不计数、CSV 忽略交易状态、账户无法管理和缺少删除全部数据等确定性问题。

## 3. P0：交易事件语义仍不完整

### 3.1 已复现的高风险样例

以下结果来自当前代码的本地预览/CLI 对抗性检查，不代表都能静默入账；但它们证明候选层可能给用户提供错误事实。若账户可由最近账户补齐，部分候选可能只差一次人工确认。

| 输入                   | 当前观察                           | 正确行为                          |
| ---------------------- | ---------------------------------- | --------------------------------- |
| `我给员工发工资8000元` | 识别为收入，并出现严重金额放大风险 | 支出 8000；主体和方向必须参与解析 |
| `红包200元`            | 支出/其他支出，无方向歧义          | 未说明收发，应阻断                |
| `在医院停车10元`       | 医疗健康                           | “停车”应优先于医院场所，归交通    |
| `给孩子交学费3000元`   | 类型、分类缺失                     | 应识别教育支出                    |
| `转给老王100元`        | 类型缺失                           | 转账流出，保留对方                |
| `老王转给我100元`      | 类型缺失                           | 转账流入，保留对方                |
| `我还老王100元`        | 类型缺失                           | 还款流出                          |
| `押金退回100元`        | 资金语义解释不完整                 | 押金返还/退款方向明确后再确认     |
| `闲鱼卖手机800元`      | 类型缺失                           | 二手出售收入                      |
| `在学校买饭10元`       | 分类缺失                           | 明确商品动作优先，归餐饮          |
| `花呗分期手续费10元`   | 其他支出                           | 应归金融费用内部语义              |

### 3.2 非结算语言会生成候选

当前系统能正确阻断一部分失败和否定表达，例如“支付失败”“付款已取消”“尚未到账”，但覆盖不完整：

| 输入                     | 当前观察         | 风险                      |
| ------------------------ | ---------------- | ------------------------- |
| `差点花了100元`          | 生成支出候选     | 反事实被当成真实支出      |
| `朋友说他花了100元`      | 生成支出候选     | 他人转述进入我的账本      |
| `提醒我明天交房租2000元` | 生成住房支出候选 | 提醒/未来计划被当成已结算 |
| `商家报价100元`          | 生成候选         | 报价不是交易              |
| `预算1000元`             | 生成候选         | 预算不是交易              |
| `余额1000元`             | 生成候选         | 余额不是资金变动          |
| `信用卡账单1000元`       | 生成候选         | 账单金额不等于已还款      |

### 3.3 根因

当前解析主干以动作词、金额、特殊关键词和分类本体组合为主，缺少独立的事件事实层。分类模型只能给类别建议，不能补齐主谓宾、否定范围、引语归属或结算状态。

建议在金额和分类之前增加结构化事件门：

```text
settlementState = COMPLETED | FAILED | CANCELLED | PLANNED | QUOTED | REPORTED | UNKNOWN
actor = SELF | OTHER | MERCHANT | UNKNOWN
direction = INFLOW | OUTFLOW | INTERNAL_TRANSFER | UNKNOWN
fundSemantics = PURCHASE | INCOME | REFUND | TRANSFER | DEBT | DEPOSIT | PREAUTH | TOP_UP
```

只有 `COMPLETED + actor/direction 明确` 的候选才能进入普通一次确认。其余候选应解释性阻断，而不是让分类或最近账户掩盖结构性不确定。

## 4. 分类模型与个性化的真实边界

### 4.1 当前模型不是完整语义模型

随包分类模型仍是 `0.1.0-bootstrap`，主要来自约 2,352 条模板/种子样例。它擅长商品或机构到一级分类的映射，不擅长：

- 主谓宾和资金方向；
- 否定、反事实、计划和转述；
- 结算状态；
- 多义实体，例如“苹果”是水果还是手机；
- 场所和真实消费对象的冲突。

“自动学习纠正”当前主要是同一商户连续三次纠正后生成本地规则，并不是在设备上持续重训完整模型。产品文案和验收指标应准确表达这一点。

### 4.2 模型资格门使用人类文案匹配

模型是否可以参与分类，部分依赖对可读 `ambiguityReasons` 做正则匹配。这会把安全策略绑定到中文提示文案：未来改写一句提示，可能无意改变模型资格。

应改为稳定的结构化 reason code 和字段所有权，例如：

- `AMOUNT_MULTIPLE_CANDIDATES`
- `SETTLEMENT_NOT_COMPLETED`
- `DIRECTION_UNKNOWN`
- `SPECIAL_FUND_SEMANTICS`
- `CATEGORY_ONLY_UNCERTAINTY`

模型只能消解 `CATEGORY_ONLY_UNCERTAINTY`，不能触碰金额、方向、账户和结算状态。

### 4.3 评估证据不足

当前没有授权真实财务语言的冻结盲测，不能用合成模板准确率或个别正确截图代表生产准确率。至少应报告：

- accepted precision 与 coverage；
- 九个一级标签的逐类召回；
- 商户/用户/提示族隔离后的测试结果；
- 退款、充值、押金、转账、借还款、交通票务等风险切片；
- 模型弃权率和 calibration；
- 端到端金额、类型、分类同时正确率。

## 5. 分类与确认交互不一致

### 5.1 一级分类策略尚未贯穿全 App

确认卡和手动记账已主要只让用户选择一级分类，这是正确方向。二级分类应继续保留稳定 ID，供内部模型、规则、历史数据和可选分析使用，不能删除历史分类。

但以下页面仍不一致：

- 流水、首页和待确认展示层仍可能显示“一级 / 二级”；
- 预算页面展示所有一级与二级分类；
- 周期账只允许选择叶子/二级分类；
- 用户无法在普通交互中纠正内部二级标签，二级模型也难获得可靠人工反馈。

推荐统一：普通选择、预算、周期账和默认流水只使用一级分类；二级分类只在详情或高级分析中弱化展示。

### 5.2 缺失字段会强迫进入完整编辑页

确认卡只渲染已经识别出的字段。即使金额和分类都正确、只缺账户，也会提示用户进入完整编辑页，而不是在卡片中补一个账户。

建议：

- 只缺账户、一级分类或可选备注时在卡片内补齐；
- 金额冲突、方向冲突、特殊资金语义才进入完整编辑；
- 增加轻量“为何这样分类”，但不增加确认步骤。

### 5.3 备注设计合理

可选备注适合记录用途、同行人、报销背景和用户自定义信息。它不应成为必填字段，也不能替代退款、转账、押金等结构化资金类型。

## 6. P0/P1：预算存在确定性逻辑错误

预算页面加载全部可见支出分类，允许给二级分类设置预算；交易分析结构只按一级 `categoryId` 汇总，不包含 `subcategoryId`。

例如：

```text
预算：餐饮 / 午餐 = 1000 元
交易：categoryId = 餐饮，subcategoryId = 午餐
统计：用午餐 ID 查一级分类汇总
结果：午餐预算消费显示为 0
```

修复要求：

1. 预算 UI 只展示一级分类；
2. Repository 保存层拒绝二级分类 ID，不能只靠 UI；
3. 对已存在二级预算做兼容映射或明确迁移策略；
4. 增加二级预算不得静默失效的回归测试；
5. 避免 ScrollView 一次渲染上百个输入框。

## 7. 账户体系缺少产品入口

数据库已有账户实体和使用频率排序，但没有账户管理页面。用户无法：

- 新增银行卡、现金或自定义账户；
- 重命名和隐藏账户；
- 区分多张同类型银行卡；
- 配置尾号或导入别名；
- 调整默认/常用账户。

这会直接降低账单导入和智能记账的账户命中率。建议新增简洁账户管理，不扩张为复杂资产负债产品；删除/隐藏前必须检查历史引用。

## 8. CSV 账单导入仍是工程原型

已有优点：解析在本地完成、单批事务原子、同来源单号确定重复跳过、弱指纹疑似重复标记、导入结果只进入待确认。

明确缺口：

1. UI 要求复制整段 CSV 到文本框，不是真正文件选择；
2. 解析器支持自定义列映射，但 UI 没有映射流程；
3. 预览只展示前 20 条，无法逐条排除或编辑；
4. 失败行只显示数量，不能查看完整原因；
5. 微信/支付宝“当前状态/交易状态”列未纳入 schema；
6. 失败、取消、退款处理中等行可能进入候选；
7. 未知类型且正金额会回落为收入；
8. `转入/转出` 被简化成收入/支出，而不是账户转账；
9. 同一分钟、同金额、同商户、同账户的真实连续交易会成为疑似重复；
10. 疑似重复会整体进入待确认，用户不能在导入预览阶段排除。

下一步必须优先把交易状态、退款和转账映射纳入结构化解析，再完善文件选择、列映射和逐条预览。

## 9. 周期记账仍是最小原型

周期账只生成待确认草稿是正确安全边界，但当前可用性不足：

- 保存模板后立即生成首笔，不能选择开始日期；
- 只支持每周/每月，不能选择星期或每月日期；
- 没有结束日期、暂停到某天或跳过一次；
- 创建后不能编辑名称、金额、分类、账户和周期；
- 只能删除重建；
- 强制选择二级分类，与一级分类策略冲突；
- 列表不展示下一次生成时间；
- 模板多后 ScrollView 全量渲染。

## 10. 数据、迁移与备份

### 10.1 缺少删除全部数据

这是隐私和发布阻断项。删除范围必须覆盖：

- 已确认、待确认、软删除交易和标签；
- 分类反馈、用户规则、商户学习；
- 预算和周期模板；
- 导入记录、通知候选和去重状态；
- Agent/语音幂等回执；
- 模型 shadow 观察；
- 原始文字、设置和本地缓存。

操作应要求系统身份验证、二次确认和可验证的原子清理结果。

### 10.2 迁移测试起点不足

数据库已到 v12，但当前显式升级测试主要覆盖 v1-v5 起点。迁移哈希只能证明历史 SQL 未修改，不能证明 v6-v11 的真实数据升级后金额、关联、统计和新表默认值正确。

必须补齐 v1、v6、v7、v8、v9、v10、v11 到 v12 的冻结数据库 fixture，并验证失败回滚、future schema 拒绝和升级后业务统计。

### 10.3 备份恢复边界

已有 AES-256-GCM、PBKDF2-HMAC-SHA256、校验和、外键和事务原子恢复。仍有以下缺口：

- 明文备份文档上限约 32 MiB；
- 超限后 CSV 不能替代包含规则、设置和幂等记录的完整备份；
- 恢复前没有只读预检和交易/规则/设置数量摘要；
- 缺少填充 v7-v12 各新表的跨版本完整恢复矩阵；
- SQLite 本身未做数据库级加密，账本锁只保护 UI。

## 11. 隐私、通知与 OCR

### 11.1 已有安全基础

- Android Manifest 移除 `INTERNET` 与 `ACCESS_NETWORK_STATE`；
- 通知/OCR 默认关闭；
- 导入只进入待确认；
- Android 禁用系统备份；
- 原始文字可关闭并事务清理；
- App 锁、金额隐藏和任务缩略图保护已有源码；
- 加密备份不保存口令。

### 11.2 通知权限的真实边界

Android 通知访问授权在系统层面对所有通知具有高信任成本。App 内包名和支付词过滤只能减少应用保存的数据，不能缩小系统授予的权限范围。还缺少：

- 多 OEM 后台存活；
- 微信/支付宝格式变化；
- 通知修改、撤销、重复、延迟；
- 至少 100 条授权真实通知的 precision/coverage；
- 权限撤销和清理后的真机验证。

### 11.3 OCR 与包体

Android ML Kit 中文 OCR 和 iOS Vision 属于实验入口。当前优化 APK 仍约 68 MiB，OCR/原生依赖是主要体积来源之一。所有用户不应为低使用率实验能力承担固定体积，建议评估动态模块、独立实验包或放弃。

### 11.4 App 锁不是数据库加密

隐私锁能阻止普通旁观者进入 UI，但不能对抗 root、设备取证或高权限恶意软件。发布文案必须准确描述威胁边界，Internal debug 签名 APK 也不应承载正式重要账本。

## 12. Android 离线语音

### 12.1 已有安全设计

- App 自持 `AudioRecord`；
- 16 kHz mono PCM16；
- PCM 不跨 React Native、不落盘、不上传；
- partial 只预览，手动 stop 是唯一 final；
- cancel、后台、30 秒超时和迟到回调不能提交；
- 模型、Runtime、许可证和 SBOM 由 SHA-256 锁定；
- 能力损坏时 fail closed，不伪装成 OEM 回退。

### 12.2 仍未闭环

- 财务 ASR manifest 只有约 238 个文本槽位，没有完整授权录音；
- 未完成至少 300 条真实财务语音冻结盲测；
- `asym-full` 是激进量化体积候选，自动指标存在退化，不能由个别主观样例提升为默认；
- 缺少红米 K90 的 100 轮、PSS、线程、句柄和温升；
- 缺少来电、闹钟、锁屏、后台、权限撤销和录音抢占；
- 最新分类 hotfix APK 是受控增量打包，不是从全部锁定依赖开始的干净重建；
- iOS 尚无同等 App 自持离线流式能力。

结论只能表述为“单机体验明显改善/候选可验证”，不能表述为“离线语音已经解决”。

## 13. 分析与洞察边界

已有统计能排除待确认、软删除、疑似重复和转账/债务，并让关联退款冲减原支出，这是正确基础。

仍需关注：

- 二级分类预算错误会污染预算结论；
- 分类规则或父子分类变化可能造成跨月趋势不连续；
- “订阅候选”依赖相同商户、相同金额和 25-35 天间隔，会漏掉浮动金额订阅，也可能把房租或重复消费当订阅；
- “连续三个月增长”只反映严格单调趋势，稀疏样本时容易过度解释；
- 洞察应标记为候选或提示，不能替代账本事实。

## 14. 性能、无障碍和多设备适配

当前风险包括：

- 预算、周期账、部分待确认/规则页面使用 ScrollView 全量渲染；
- 预算页面可能一次创建上百个 TextInput；
- 没有 TalkBack/VoiceOver 真机报告；
- 没有大字体、屏幕缩放、键盘遮挡、小屏和折叠屏验收；
- 底部导航限制字体放大，可能压缩无障碍文字；
- 固定浅色视觉，没有完整深色模式；
- 没有平板布局和 iOS Dynamic Type 证据；
- 长备注、长商户名和中英文混排仍需截断/换行测试。

## 15. 工程、CI 与发布证据

1. 当前研究分支已经推到 GitHub，但没有对应新 PR；
2. 当前 HEAD 没有 GitHub Actions run；
3. `main` 仍明显落后于 v12 与最新分类/语音研究；
4. 当前只有一个综合 workflow，iOS 完整编译依赖锁文件存在；仓库目前缺少两个 iOS 锁文件；
5. Internal APK 使用 debug 证书，不是生产签名；
6. 版本仍为 `1.0.7 (8)`，但功能和数据库已跨越多轮变化，产物身份容易混淆；
7. 干净离线构建依赖外部模型和 Runtime 资产，当前缺失锁定 Compact AAR；
8. 安全威胁模型、发布手册和早期进展文档部分内容已经过时。

## 18. 推荐执行路线

```text
第一阶段：事实安全
  交易事件门 -> 工资/转账/转述/计划对抗集 -> CSV 状态映射

第二阶段：确定性数据问题
  预算修复 -> 删除全部 -> v6-v12 迁移/恢复矩阵 -> 账户管理

第三阶段：统一低负担交互
  一级分类投影 -> 卡片内补齐 -> 周期账完善 -> CSV 预览

第四阶段：真实设备与数据
  20-50 条快速语音集 -> 300+ 冻结集 -> 100 轮/OEM/隐私生命周期

第五阶段：发布工程
  新 PR/CI -> 干净 APK -> 生产签名 -> 版本升级 -> 灰度与回滚
```

只有在事实安全和数据完整性完成后，才值得继续扩大模型、OCR、通知或 Agent 的能力范围。
