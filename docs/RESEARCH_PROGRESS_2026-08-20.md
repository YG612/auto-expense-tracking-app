## 1. 结论先行

轻记 AI 当前已经形成一条相对完整的 local-first 记账链路：用户说或输入一句话，应用在本地解析金额、交易类型、分类、账户与时间，必要时要求人工补充，再以幂等方式写入本地账本。研发重点始终是“金额正确、避免重复、减少操作、隐私优先”，而不是追求无条件自动入账。

截至 2026-08-20，当前本地审查分支已经完成以下工作：

1. 将 PR #11 的本地分类模型、交易对手提取、通知/OCR 实验和 Agent 接口与远端 `main` 的 CSV、加密备份、隐私锁、预算及循环账功能重新集成。
2. 解决 PR #11 与 `main` 在数据库迁移编号、备份表、原生模块和界面上的冲突。
3. 将确认页和待处理页的分类选择器精简为一级分类；二级标签继续保留给模型、规则和内部统计，不再要求普通用户从冗长列表中选择。
4. 在确认卡片中加入可选备注字段；备注不是必填项，不影响快速确认路径。
5. 修复普通 Internal APK 意外打入四套 ABI、包体达到约 198 MiB 的问题；现在普通与流式 Internal 均强制为 `arm64-v8a`。
6. 移除 Internal 构建不需要的悬浮窗权限，并增加最终 APK 权限、ABI 和语音载荷门禁。
7. 在当前源码上重新构建普通 arm64 Internal 和 streamingAsr arm64 Internal，并完成权限、模型/runtime、许可证、SBOM、签名及 16 KB 对齐静态审计。

当前仍不能称为生产就绪，主要原因是：

- PR #11 仍处于 Open 状态，GitHub 判定 `mergeable=false`、`mergeable_state=dirty`，不能直接合并。
- 当前没有连接红米 K90 或其他 ADB 真机，APK 尚未完成安装、升级、权限和稳定性验证。
- 分类模型只有合成/模板数据和少量人工观察证据，尚未通过授权真实财务语料的冻结盲测。
- iOS 在 Windows 上只完成源码与工程静态检查，没有完成 Xcode 编译、签名或真机验证。
- 通知监听、OCR、iOS Share Extension 和 Agent 自动化仍属于高信任成本实验入口，需要独立验收。

## 3. 核心记账能力

### 3.1 金额和分句

当前确定性解析器已经覆盖：

- 单笔普通支出和收入；
- 数量乘单价、前置或后置单价；
- 中文数量；
- “半斤”“两斤半”等口语数量；
- 一句话中的多笔交易按事件拆分；
- 退款、转账、借款、还款等特殊资金语义隔离。

以下情况保持 fail closed：

- 数量或单价为负；
- 文本中的总价与计算结果冲突；
- 促销描述存在，但实际支付金额不明确；
- 同一句存在多个互相冲突的金额；
- 退款、充值、押金、会员卡、代金券等特殊资金语义无法确定。

模型不能决定金额、账户、交易性质或是否写账；这些关键字段仍由确定性规则和人工确认控制。

### 3.2 分类规则层级

当前分类优先级为：

1. 用户明确写出的分类；
2. 用户规则；
3. 已验证商户规则；
4. 商户/机构词典；
5. 轻量本地分类模型或语义本体；
6. 普通关键词回退。

场所词不再覆盖明确商品或服务，例如：

- “在网吧上网”可归为娱乐；
- “在网吧买水”应归为餐饮；
- “在网吧买鼠标”应归为购物。

充值、押金、退款和储值等风险语义会阻止普通场所回退，避免把特殊资金流错误写成消费。

本轮还修复了几类模型/商户误判来源：

- “到账”“收到”不应被误当作商户名称；
- 行程目的地不应直接变成交易对手；
- “机票”等商品/服务词不应被提取为商户。

## 4. 本地分类模型研究

### 4.1 当前模型组成

当前随包模型为 fastText 0.9.2 量化模型：

- 模型 ID：`qingji-bill-category-fasttext`
- 版本：`0.1.0-bootstrap`
- taxonomy：version 2
- 15 个分类 `.ftz` 模型头；
- 1 个交易对手候选模型；
- APK 内 `bill-classifier` 资产压缩后约 2.25 MiB；
- 每个模型文件均由 manifest 的大小和 SHA-256 锁定，并包含 notices 与 SBOM。

当前阈值：

| 输出     | 最低置信度 | 最低 margin |
| -------- | ---------: | ----------: |
| 一级分类 |       0.82 |        0.18 |
| 二级分类 |       0.78 |        0.15 |

模型输入最多 500 字符，预处理会弱化日期、金额、订单号等易过拟合标识。模型加载、校验、推理失败、超时或置信度不足时，都会回退到确定性分类结果。

### 4.2 已观察到的正向结果

用户在真机界面输入“今天下午买了武汉飞云南的机票花了796”，当前候选正确提取：

- 金额：`796.00`
- 类型：支出
- 一级分类：交通
- 账户：微信

这说明分类模型/规则组合对该样例产生了有效结果，尤其是没有把“武汉”“云南”或“机票”误提取为商户分类。

但这只是一条正向观察样例，不能据此宣称模型总体准确率已经达标。当前 bootstrap 模型主要来自 2,352 条种子分类名、通用别名和中性模板，尚未经过授权真实财务语言的独立盲测。

### 4.3 模型边界

模型只负责提出分类建议，不能：

- 解析或修正金额；
- 选择账户；
- 判断退款、转账、借还款等特殊资金类型；
- 直接写入数据库；
- 绕过确认；
- 因模型置信度高而开启静默自动入账。

目前代码中已有下一代九标签单头模型的训练、评估、校准和 shadow 流程，但新的权重尚未通过 LLM-only 数据发布门禁，也没有被提升为随包正式资产。

## 5. 分类选择与备注体验

### 5.1 为什么只给用户一级分类

截图中的旧分类选择器把“家电、打印复印、捐赠、汇兑费用、火车高铁、牙科、物业、签证、视频会员”等二级标签平铺给用户。虽然这些标签对模型训练、细粒度分析和规则解释有价值，但会带来三个问题：

1. 用户需要理解系统内部 taxonomy，记一笔账的认知负担过高；
2. 同类标签数量会随模型研究增长，界面越来越长；
3. 用户只是想纠正“餐饮/交通/购物”等大类，却被迫做模型标注工作。

因此当前实现改为：

- 用户只选择一级分类；
- 二级分类继续保留在模型候选、规则和底层数据结构中；
- 用户保持同一一级分类时，可以保留模型已经识别出的二级分类；
- 用户主动改为另一个一级分类时，清除原二级分类，避免旧子类与新父类冲突；
- 历史账不迁移、不重写，稳定的 `systemKey` 和 `categoryId` 保持兼容。

这不是删除分类知识，而是把“内部分类精度”和“用户操作复杂度”分层。

### 5.2 可选备注

确认卡片已在分类和账户附近增加备注输入框：

- 可填可不填；
- 不影响金额、分类和账户的快速确认；
- 适合记录同行人、用途、订单说明、报销信息等模型不应猜测的内容；
- 不用新增更多二级分类来承载个性化信息。

备注不能替代特殊资金类型，也不能用来掩盖金额或账户歧义。

## 6. 确认、幂等与 Agent 安全

### 6.1 一次确认路径

信息完整时，用户可直接在候选卡片确认入账；最近使用账户只能作为提示，仍需用户确认。金额或关键语义存在歧义时继续阻断。

待处理卡片支持：

- 编辑金额；
- 修改一级分类；
- 修改账户；
- 补充可选备注；
- 批量补充缺失信息；
- 放弃或保存为待处理。

### 6.2 防重复入账

已实现多层幂等保护：

- speech draft/turn generation；
- 一次性 result token；
- consume/reset 屏障；
- 完成、放弃、再记一笔或离开页面后的迟到回调失效；
- 数据库 `recognized_operation_receipts` 与交易在同一 SQLite 事务提交；
- 语音 origin 和 canonical payload hash 共同参与判重；
- 同一语音重放、payload mismatch 和软删除后重放均明确拒绝。

PR #11 还增加 Agent command、同步协议和 operation receipt。当前原则不变：Agent 可以提交待确认候选，但不能绕过人工确认直接修改账本。

## 10. 2026-08-20 Android 构建与产物审计

### 10.1 构建中发现并解决的问题

1. **冷缓存离线构建缺少 ML Kit 依赖**  
   首次普通包构建因 `com.google.mlkit:text-recognition-chinese:16.0.1` 不在本地 Gradle 缓存而失败。联网按锁定版本补齐依赖后，离线重建成功。新环境若要求完全离线构建，仍需预置该依赖。

2. **普通 Internal 混入四套 ABI**  
   原构建同时包含 `arm64-v8a`、`armeabi-v7a`、`x86` 和 `x86_64`，APK 达到 207,838,037 bytes，约 198.2 MiB。根因是 React Native 新架构仍读取四 ABI 默认值，仅设置 Gradle `abiFilters` 不足。

   修复后：

   - Windows Internal 构建入口默认并强制 `reactNativeArchitectures=arm64-v8a`；
   - Internal build type 同时设置 arm64 `abiFilters`；
   - 普通 APK 最终后验要求原生 ABI 集合严格等于 `{arm64-v8a}`；
   - 非 arm64 Internal 参数会在构建前被拒绝。

3. **Internal 混入悬浮窗权限**  
   Internal 为了链接 React Native debug native artifacts 使用 debug fallback，间接合入 `SYSTEM_ALERT_WINDOW`。该包不使用 Metro overlay，因此已在 Internal manifest 中显式移除，并把悬浮窗加入普通包禁止权限门禁。

错误的四 ABI 临时 APK 已删除；它只是可重建的构建产物，不包含用户数据。

## 14. 证据级别说明

本文使用以下口径：

- **源码存在**：代码或资源位于仓库中，不代表能编译或运行。
- **自动测试通过**：指定测试在当前本地提交通过，不代表真机稳定。
- **APK 可构建**：Gradle 生成了可验证 APK，不代表已经安装。
- **静态产物通过**：权限、ABI、哈希、签名和对齐符合门禁，不代表功能正确。
- **真机通过**：必须在记录设备、系统、安装路径和测试矩阵后才能声明。
- **生产就绪**：还需要迁移、备份恢复、准确率、稳定性、隐私、签名和灰度证据。

当前项目达到“本地集成源码 + 自动测试 + Android Internal 静态产物”阶段，尚未达到“目标真机完整验证”或“生产发布”阶段。
