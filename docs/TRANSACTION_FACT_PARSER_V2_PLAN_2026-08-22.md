- 基线分支：`codex/pr11-integration-20260820`，HEAD `55fe791`
- 实施分支：`codex/transaction-facts-v2`

## 1. 决策

采用“候选事实提取 → 联合解析 → 一致性门禁 → 兼容投影”的 V2 解析器，保留现有事件切分、日期、账户、分类本体、确认页和持久化安全边界。

不采用以下方案：

1. 继续把同义动作分别追加到金额、类型、商户和方向正则。该方案无法保证四个字段使用相同语义，规则数量随表达组合增长。
2. 直接用端侧分类模型覆盖整条解析链。现有模型只支持收支分类和对手方候选评分，不负责金额、结算状态、方向与资金性质；让模型直接写关键字段也不满足可审计和 fail-closed 要求。
3. 一次性删除旧解析器。当前规则已经覆盖取消、计划、报价、转述、多事件、单价和优惠等大量安全边界，必须增量迁移。

可行性依据：

- 当前语义分类器已经使用带 span、role、evidence、`RESOLVED / AMBIGUOUS / ABSTAINED` 的模式，证明该结构与现有 TypeScript 架构兼容。
- `parseAmount()` 已暴露数字 mention 和证据，增加可选的事实上下文即可避免复制金额实现。
- `ParsedTransactionCandidate` 支持增加可选审计字段，不改变数据库实体或旧调用者。
- 持久化层已经根据缺失字段、歧义和确认意图二次校验，可以承接 V2 的弃权结果。

## 2. 当前根因

现有 `parseTextTransactions()` 依次独立调用金额、类型、商户和事件事实解析器。每个解析器重新读取整段文本，没有共享：

- 动作的规范语义和位置；
- 金额、数量、日期、账户的 span；
- 付款人、收款人、商户、地点和平台的角色；
- 字段之间的一致性约束。

因此 `给老王发了67块` 同时出现：

- `老王发了` 被兜底规则当作商户；
- `67块` 因 `发了` 不在金额动作表而被当作数量歧义；
- 类型和方向无法识别。

在 18 个 `给老王 + 发/转/打/汇/付/支付 + 67元/块/块钱` 等价样本中，当前结果为：金额 14/18、商户 0/18、方向 9/18，三项同时正确 0/18。

## 3. 目标数据结构

V2 对每个已切分事件生成一个 `TransactionFactResolution`：

```ts
type TransactionFactResolution = {
  status: 'RESOLVED' | 'AMBIGUOUS' | 'ABSTAINED' | 'NO_MATCH';
  action?: FactEvidence<CanonicalAction>;
  direction?: FactEvidence<'INFLOW' | 'OUTFLOW' | 'INTERNAL_TRANSFER'>;
  fundSemantics?: FactEvidence<FundSemantics>;
  transactionType?: FactEvidence<TransactionType>;
  payer?: ParticipantFact;
  payee?: ParticipantFact;
  counterparty?: CounterpartyFact;
  moneyRanges: TextSpan[];
  evidence: TransactionFactEvidence[];
  conflicts: TransactionFactConflict[];
};
```

每个事实必须包含规则 ID、原文 span 和确定性级别。最终字段只能来自已解析事实或现有专用解析器，不能来自无来源的字符串截取。

## 4. 语义边界

### 4.1 动作与资金性质分离

动作只描述语言表面：

- `PAY`：付、支付、付款；
- `SEND_MONEY`：发、打、汇、转、划；
- `SPEND`：花、消费、扣款；
- `RECEIVE_MONEY`：收、收到、到账；
- `PURCHASE`：买、购买、下单；
- `REPAY / LEND / BORROW / REFUND / TOP_UP`：保留专门语义。

`SEND_MONEY` 不能单独决定经济性质。只有两个本人账户时才是内部转账；对个人付款无用途时保留资金转移语义并要求确认，不猜测消费分类。

### 4.2 对象角色分离

- `PERSON`：老王、朋友、孩子等个人对手方；
- `MERCHANT`：存在交易关系的商家或机构；
- `VENUE`：北京、学校、医院等地点；
- `PLATFORM`：淘宝、美团等交易平台；
- `PAYMENT_CHANNEL`：微信、支付宝等账户或渠道。

兼容期可以把高可信个人对手方投影到 `merchantRawName` 供旧 UI 展示，但必须同时标记 `counterparty.kind = PERSON`，并保持个人交易人工确认。动作、金额、渠道和地点不得进入对象 span。

### 4.3 金额与数量

`块` 仅在以下情况下直接作为金额：

- 整段只有金额；
- 有明确币种或角分后缀；
- 数字 span 与已解析资金动作属于同一事件框架；
- 现有明确消费上下文成立。

`买3块面包` 仍按数量；`给老王发了3块` 按金额。事实层只提供 money range，不复制数值换算逻辑。

## 5. 一致性门禁

生成候选前必须检查：

1. 实体 span 不得与动作、金额、日期、账户或渠道 span 重叠。
2. PERSON 不得静默升级为 MERCHANT。
3. 每个金额只能绑定一个事件；总价与分项沿用现有对账规则。
4. payer/payee 必须与方向一致。
5. 内部转账必须有两个本人账户；对外付款不得要求“转入账户”。
6. 交易类型与资金性质必须兼容。
7. 普通支出分类只能在已完成且支出语义成立时运行。
8. 冲突、同分多解或关键事实低可信时返回歧义或弃权，不能用其他字段的分数抵消。

## 6. 置信度

继续保留旧 `confidence` 输出，但 V2 增加关键事实置信度。最终可确认置信度以关键字段最低值和一致性门禁为准，不再因错误商户存在而提高。

首阶段规则：

- 事实冲突：最多 `LOW`；
- 使用个人对手方兼容投影：必须产生人工确认原因；
- 使用低可靠兜底对象：不得 `DIRECT_CONFIRM`；
- V2 未识别时完全保留旧结果，但记录影子差异，不改变发布行为。

## 7. 迁移阶段

### 阶段 A：基础设施

- 建立版本化统一动作词典。
- 实现 span/evidence/fact/conflict 类型。
- 实现个人资金发送/接收框架和 money range。
- 建立事实层独立测试，不接数据库。

### 阶段 B：兼容接入

- `parseAmount()` 接受可选 money range。
- 类型、对象和事件事实优先使用无冲突 V2 事实。
- `ParsedTransactionCandidate` 增加可选 `factResolution` 审计字段。
- 修正内部转账与个人对外付款的目标账户要求。
- V2 无结果时回退现有逻辑；V2 有冲突时 fail closed。

### 阶段 C：一致性与置信度

- 增加跨字段一致性校验。
- 对错误对象 span、方向冲突、经济性质冲突产生稳定 reason code。
- 将 V2 关键事实结果纳入确认决策。

### 阶段 D：覆盖扩展与模型影子

- 扩展购买、退款、借贷、报销、代付和多事件框架。
- 端侧模型只生成候选事实或分类建议，不能绕过一致性门禁。
- 使用影子差异和人工黄金集决定是否扩大接管范围。

## 8. 测试与验收

### 黄金断言

每个样本断言完整结果，包括应不存在的字段。禁止只断言金额和分类而忽略错误商户。

### 变形不变量

- `元 / 块 / 块钱` 在同一资金动作中结果等价；
- `发 / 打 / 汇 / 转` 在同一人物资金框架中产生相同参与者和方向；
- 增加微信/支付宝只能影响账户，不得改变人物、金额和用途；
- 标点和无害语序变化不得改变事实；
- `买3块面包` 与 `花3块买面包` 必须保持数量/金额差异。

### 负向样本

- 计划、报价、失败、取消、反事实、他人转述；
- 地点不是商户；
- 支付渠道不是商户；
- 个人不是内部账户；
- 数字是日期、编号、数量或折扣时不得成为金额。

### 门禁

1. 新事实解析器单测通过。
2. 当前 267 个相关测试零回归。
3. TypeScript、ESLint、格式检查通过。
4. 全量 Jest 通过。
5. 原 worktree 保持 clean，HEAD 和分支不变。
6. 不新增数据库迁移、不修改 Android/iOS 语音模型资产。
